# Proba — бриф агенту для разработки backend

Ты пишешь backend платформы Proba вместе с Кириллом (Go-разработчик, соло-основатель). Этот файл и `openapi.yaml` рядом с ним — источник правды. Если что-то в них противоречит друг другу или реальности, не угадывай: остановись и задай вопрос (раздел «Открытые решения»).

## 1. Продукт в двух абзацах

Proba — приложение для осознанного потребления напитков: кофе, пиво, вино. Ядро — единая модель «проба» (дегустация): оценка, оси вкуса, колесо вкусов, место, компания. Поверх неё вкусовой профиль, рекомендации, паспорт вкуса (уровни и бейджи), лента.

Модель B2B2C. В v1 только B2C-ядро. Заведения появляются органически: когда у места накопилось достаточно проб, ему автоматически открывается кабинет. Монетизация отложена до сигнала от заведений. Цель — работающий MVP у первых пользователей к 31.12.2026. Рынок — Россия, online-first.

Дизайн готов на весь функционал (41 экран: приложение, кабинет заведения К1–К8, админка А1–А9). Принцип: **всё, чего ещё нет на backend, клиент прячет фича-флагом.** Поэтому контракт описывает весь макет, а реализуется по фазам.

## 2. Что в комплекте

- `openapi.yaml` — контракт (OpenAPI 3.0.3, 174 операции, проходит валидатор). У каждой операции: `x-phase` (1–4), `x-flag` (флаг, под которым она живёт), `x-module` (модуль-владелец), `x-screen` (экран макета). Реестр флагов — `x-flags` в корне.
- Дизайн-макет (Claude Design artifact) — экраны, на которые ссылается `x-screen`. Данные в нём примерные.

## 3. Стек (зафиксирован, не менять без разговора)

Go, zerolog. Yandex Serverless Containers (именно контейнеры, не Cloud Functions). YDB Serverless, Object Storage, API Gateway, Yandex Message Queue. Мониторинг: Yandex Monitoring + Grafana Cloud free. Код на SourceCraft. ClickHouse и DataLens отложены. Мобильный клиент: React Native + Expo (EAS, Dev Client) на TypeScript.

Что из этого меняет привычные решения:
- **YDB, не Postgres.** Нет схем на модуль: изоляция через префикс таблиц/каталог (`/users/...`, `/tastings/...`). Нет JOIN через границы модулей и внешних ключей, ссылки на чужие сущности хранятся как UUID. Полнотекстового поиска и PostGIS нет: поиск по каталогу в фазе 1 — префиксы и нормализованные токены, гео — geohash-колонки с постфильтром в Go.
- **Serverless Containers масштабируются до нуля.** Фоновая горутина (outbox-релей, воркеры) между запросами может не жить. Ничего критичного не должно зависеть от фонового процесса в том же контейнере.
- **YMQ — at-least-once.** Все консьюмеры идемпотентны, у каждого события стабильный `event_id`.

## 4. Архитектура: модульный монолит, из которого легко вынуть сервис

Один `go.mod`, один деплой, но границы жёсткие, как у сервисов.

```
cmd/api/main.go             composition root: собирает модули, поднимает HTTP
internal/platform/          config, zerolog, ydb-клиент, http, middleware, flags, events, idempotency
internal/modules/<name>/
  api.go                    публичный интерфейс модуля + DTO (единственное, что видят другие)
  module.go                 New(deps) -> Module: роуты, подписки на события
  internal/                 domain, app, store, transport/http (снаружи недоступно)
migrations/<name>/
```

Правила, которые проверяет CI (`depguard` / go-arch-lint), а не договорённость на словах:
1. Модуль обращается к другому только через его `api.go`. Там отдельные DTO, не доменные сущности; все методы принимают `context.Context`; ошибки доменные (`ErrNotFound`), не драйверные.
2. Таблицы модуля читает и пишет только он сам. Чужие данные — через `api.go` или через собственную read-модель, построенную по событиям.
3. Всё, что не требует мгновенного ответа, идёт событиями (`tasting.published`, `catalog.beverage_merged`, `venue.approved`). События плоские и версионируются.
4. Авторизация — JWT, проверяется локально без похода в БД. Три аудитории: `app`, `cabinet`, `admin`. Роль и `venue_id` лежат в токене.
5. Транспорт (HTTP-хендлеры) живёт внутри модуля. `cmd/api` только монтирует их.

Про события и транзакции: на старте достаточно in-process шины и публикации в YMQ после коммита. Полноценный outbox добавляем, когда появится событие, потеря которого недопустима (первый кандидат — `tasting.published` → пересчёт профиля, но он восстановим пересчётом). Не строй outbox заранее.

### Модули

Зафиксировано ранее четыре домена: users, tastings, recommendations, venues. Контракт описан чуть шире (поле `x-module`), потому что в макете есть куски, которые в эти четыре не ложатся чисто. Предлагаемое соответствие:

| Модуль | Что внутри | Фаза |
|---|---|---|
| `platform` (не домен) | конфиг, флаги, загрузки (presign), админ-вход, роли и аудит админки, рассылки | 1 |
| `users` | auth, аккаунт, профили, настройки, push-токены, оборудование, удаление данных | 1 |
| `catalog` | напитки, производители, модели вкуса, справочники, штрихкоды, дубли | 1 |
| `tastings` | пробы, вкусовой профиль, паспорт и уровни, полка, вишлист, запасы, чеки | 1–3 |
| `venues` | заведения, меню и остатки, чекины, бонусная карта, кампании, команда, аналитика | 2–3 |
| `social` | лента, подписки, лайки, комментарии, жалобы, клубы, «Передать рядом» | 2–4 |
| `recommendations` | «Для вас», свайп-колода, похожие люди, AI-чат и разбор по фото | 2–4 |
| `content` | курсы, рецепты, обучение, заваривание | 3 |
| `billing` | Proba+, тарифы заведений | 4 |

Начинай с `platform`, `users`, `catalog`, `tastings`. Остальные заводи, когда дойдёшь до их фазы. Не создавай пустые модули про запас.

## 5. Фазы

| Фаза | Цель | Операций |
|---|---|---|
| 1 | Вертикальный срез «залогировать пробу»: вход, онбординг, каталог, штрихкод, проба, вкусовой профиль | 30 |
| 2 | Открытия и B2B-хук: рекомендации, свайп, лента, паспорт, карта мест, кабинет заведения (обзор, меню, отзывы), заявки заведений, админка (флаги, каталог, модерация) | 71 |
| 3 | Заведения и контент: бонусная карта, синхронизация с кассой, уведомления рядом, полка, чеки, обучение, заваривание, команда заведения | 49 |
| 4 | AI-чат и разбор по фото, оборудование, Алиса, «Передать рядом», Proba+ | 24 |

Первая цель — **фаза 1, вертикальный срез от API до экрана** (то же сформулировано в Notion как текущий фокус). Фазу назначил я по логике зависимостей; Кирилл может её пересмотреть.

## 6. Конвенции контракта (соблюдать буквально)

- Деньги — целые копейки (`*_kop`). Оценка — целые десятые (`rating_tenths`: 85 = 8,5, шаг в UI 0,1). Никаких float для денег и оценок.
- Идентификаторы — UUID. Время — RFC 3339, UTC. Даты — `YYYY-MM-DD`.
- Списки — курсорная пагинация: `limit`, `cursor` → `next_cursor`.
- Создание проб — с `Idempotency-Key` (клиент работает офлайн и ретраит).
- Ошибки — объект `Error {code, message, details, request_id}`. Выключенная фича: 403 с `code=feature_disabled`. Валидация: 422 с `details` по полям.
- Активный профиль внутри аккаунта (личный/гостевой) — заголовок `X-Profile-Id`. Модель «аккаунт → профили» закладывай сразу, даже если эндпоинты профилей включатся в фазе 4.
- Три схемы авторизации — `appAuth`, `cabinetAuth`, `adminAuth`. Токен одной аудитории не принимается в другой.

## 7. Фича-флаги

Реестр в `x-flags`. Флаг — часть контракта: клиент получает уже разрешённые значения из `GET /config/flags` (раскатка по проценту, платформе, группе и зависимости считаются на сервере). Правила:
- Включить флаг нельзя, пока выключена его зависимость (422 `flag_dependency_off`).
- Операция под выключенным флагом отвечает 403 `feature_disabled`. Проверка — middleware, а не `if` в каждом хендлере.
- Любое изменение флага пишется в историю и журнал аудита.

Важно про значения по умолчанию: проценты раскатки в `x-flags` взяты с макета админки, это **предложение**, не факт. Шесть флагов (`notifications.morning`, `shelf.core`, `shelf.receipts`, `learn.content`, `social.clubs`, `venues.reviews`) есть в экранах, но не в реестре макета. Я пометил их `status: proposed`; их нужно подтвердить или убрать.

## 8. Порядок работы

Репозиторий на SourceCraft, маленькие законченные коммиты (conventional commits), CI с первого дня: `go vet`, `golangci-lint` (включая `depguard`), `go test ./...`.

1. Скелет: `go.mod`, `.gitignore`, README с абзацем о проекте, `.golangci.yml`, CI. Первый коммит без логики.
2. `platform`: конфиг из env, zerolog, ydb-клиент, healthcheck, middleware (request_id, auth по аудитории, флаги), идемпотентность.
3. **Спайк по YDB** (до моделирования данных, на реальной базе): транзакции, поведение при конфликтах, миграции (goose умеет YDB, проверь), запись события вместе с данными. Результат — короткая заметка в репозитории.
4. Раннер миграций по модулям.
5. `users` → `catalog` → `tastings`: срез «залогировать пробу». Контрактные тесты от `openapi.yaml` (сервер не должен отдавать то, чего нет в схеме).
6. Дальше по фазам.

Не делай: микросервисы, Kubernetes, ElasticSearch, ClickHouse, заранее написанный outbox, gRPC. Это осознанно отброшено.

## 9. Открытые решения (ответ нужен от Кирилла, не принимай сам)

1. **Модули.** Согласны ли с таблицей из раздела 4 или сворачиваем в четыре зафиксированных (users, tastings, recommendations, venues)? Главный вопрос: где живёт каталог напитков.
2. **Вход в фазе 1.** В реестре `auth.yandex_id` стоит на 0%, а в макете это основной вход. Что включено в MVP: Яндекс ID, телефон по SMS, оба, только гость? От этого зависит провайдер SMS.
3. **Платежи для РФ** (Proba+ и тарифы заведений): провайдер не выбран. Фаза 4, но модель `entitlements` стоит учесть раньше.
4. **Геозоны и «уведомления рядом».** Клиент регистрирует геозоны (у iOS лимит около 20), сервер координаты пользователя не хранит. Подтвердить подход и юридическую сторону хранения гео.
5. **Распознавание чеков и фото, AI-чат, рекомендации.** Какая модель и где живёт. Ничего в стеке пока не закреплено; в брифе по умолчанию рекомендации остаются Go-модулем за интерфейсом.
6. **Порог анонимности в аналитике заведений.** Предлагаю не отдавать группы меньше k=5.
7. **Часы в неделю на проект** — активный блокер в «Системе жизни»; от него зависит, реалистична ли дата 31.12.2026 для фазы 1 и какой её части.

## 10. Что я не проверял

Честно о пробелах, чтобы агент не принял их за факты:
- Данные в макете (цифры, имена, проценты) примерные. Модели вкуса (оси слайдеров, группы колеса) взяты из экранов для кофе, пива и вина; финальный справочник нужно утвердить.
- Особенности YDB (транзакции, ограничения, миграции) описаны по памяти и могут быть неточными. Отсюда спайк в шаге 3.
- Контракт написан по макету, а не по работающему клиенту. Первые реальные экраны наверняка потребуют правок; меняй `openapi.yaml` вместе с кодом одним коммитом.
- Вес 41 экрана не равен весу 174 операций: многие эндпоинты фаз 3–4 описаны на уровне идеи и будут уточняться при подходе к ним.
